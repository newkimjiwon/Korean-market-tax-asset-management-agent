# Korean-market-tax-asset-management-agent

한국 세무/자산관리 **에이전트를 위한 도구 레이어**. UI는 만들지 않는다.
에이전트가 필요한 정보를 붙여 쓸 수 있도록 계산과 감시 기능만 노출한다.

처음 사용한다면 **[준비할 자료와 작성 안내](docs/getting-started.md)**부터 확인하세요.
급여명세서에서 필요한 항목, 모르는 값의 처리, 예상 세금과 환급액의 차이를 설명합니다.

## 실제 근로자 정산

급여·비과세·보험료·기존 중소기업 감면·월세지원 내역으로 결정세액과 환급을
함께 계산하는 통합 경로를 추가했다. 2025·2026년을 지원하며, 귀속연도 전체
검증이 끝나지 않은 규칙은 `provisional`(예상)로 반환한다.

```bash
uv run python -m ktax examples/synthetic_settlement.json --json
```

MCP에서는 `describe_settlement_fields` → `calculate_salary_settlement` →
`recommend_salary_actions` 순서로 사용한다. 여러 자료는 `collect_salary_inputs`,
여러 변경의 합산 효과는 `compare_salary_settlements`로 처리한다.
[입력·출처·계산 범위 문서](docs/salary-settlement.md)를 참고한다.
예제는 합성 자료이며 실제 사용자 정보는 저장소에 기록하지 않는다.

아래의 기존 `Profile`·카탈로그 예제는 **공제총액을 사전에 계산해 넣는 레거시
시뮬레이션**이다. 실제 급여 원자료를 넣는 연말정산에는 위 통합 경로를 사용한다.

```bash
uv sync --extra mcp --extra dev
uv run pytest

uv run python -m ktax examples/salaried_33.json          # 시나리오 하나 계산
uv run python -m ktax examples/salaried_33.json --json   # 기계용 출력
uv run python -m ktax.server                             # MCP stdio 서버
```

## 에이전트 표면

이 도구들의 사용자는 사람이 아니라 에이전트다. 그래서 설계 기준이 다르다 —
계산이 맞는가뿐 아니라, 사전 지식 없는 에이전트가 도구 목록만 보고 올바른
다음 수를 둘 수 있는가.

**넣지 않은 필드는 '모름'이다.** 가장 중요한 규칙이다. 예전에는 아무것도
표시하지 않으면 모든 값을 안다고 보았는데, 그러면 채우지 않은 필드가 0으로
읽혀 "무주택 세대주가 아니라 공제 대상이 아닙니다" 같은 단정이 나갔다.
에이전트는 그것을 사실로 사용자에게 전달한다 — 물어본 적도 없는 사실을.
지금은 안전한 쪽이 기본이고, 확인해서 0원이면 `0` 을 명시적으로 넣는다.

**에러는 다음 수를 알려준다.** `Profile.__init__() got an unexpected keyword
argument 'salary'` 같은 메시지로는 에이전트가 회복할 수 없다. 유효한 이름을
찾는 법과 가까운 후보를 함께 돌려준다.

**물어볼 문장까지 준다.** `indeterminate` 의 각 항목에는 무엇이 없는지뿐 아니라
어디서 가져올 수 있는지(`sources`)와 사용자에게 물을 문장(`question`)이 담긴다.
`user_only` 가 true 면 외부 자료로는 알 수 없다는 뜻이다.

쓰는 순서는 서버 `instructions` 에 담겨 있다: `describe_profile_fields` →
(`collect_profile`) → `recommend_actions` → `check_thresholds` →
다음 달에 `compare_snapshots`.

## 직접 확인해 보기

`examples/*.json`은 합성 자료로 실행해 볼 수 있다. 값을 바꿔 실험할 때도 합성 값만 사용하고, 실제 개인정보는 예제 파일에 넣지 않는다. 숫자만으로는 검산이 안 되므로
적용한 규칙(`·`)과 가정(`~`)을 전부 함께 찍는다.

- `salaried_33.json` — 값을 직접 채운 형태
- `collected_partial.json` — 간소화자료·원천징수영수증에서 수집한 형태.
  자료 부족으로 판단할 수 없는 항목이 무엇인지 함께 보여준다

`--view` 로 정렬을 바꾼다: `value`(현재가치 순), `quick_wins`(노력이 가벼운 순),
`set_and_forget`(한 번 세팅하면 매년 자동), `urgent`(마감 임박).

## 왜 이 구조인가

**세법은 코드가 아니라 데이터다.** 세율과 한도는 매년 개정되고, 과거 귀속연도를
다시 계산해야 할 일도 생긴다. 로직에 상수를 박으면 해마다 코드를 뜯어야 하고
과거 재계산은 불가능해진다. `rules/data/<연도>.json` 이 단일 진실 공급원이고,
계산 모듈은 읽기만 한다.

**단일 ROI 점수를 만들지 않는다.** 절감액을 노력으로 나누면 사용자가 판단에
필요한 정보가 사라진다. 지금 5분이 있는 사람과 주말이 통째로 있는 사람은 완전히
다른 목록을 원한다. 가치와 노력을 독립된 축으로 두고, 합치는 판단은 에이전트에게
넘긴다.

**지평은 고정값이 아니라 사용자에게서 유도한다.** 같은 연금 상품도 30세와
50세에게 가치가 완전히 다르다. 나이와 인출 시점에서 지평을 계산하면 매년 답이
자동으로 달라지고, 그 변화 자체가 사용자가 다시 열어볼 이유가 된다.

**마감은 가치 점수에 섞지 않는다.** 섞으면 '급하지만 사소한 일'이 '안 급하지만
중요한 일'을 밀어내는 왜곡이 생긴다. 별도 오버레이로 얹는다.

**모든 계산에 근거가 붙는다.** 숫자만 뱉는 도구는 에이전트를 앵무새로 만든다.
적용 규칙과 가정을 함께 반환해서 에이전트가 "왜 이 숫자인지" 설명할 수 있게 한다.

**도구는 상태를 저장하지 않는다.** 프로필과 스냅샷은 매 호출 인자로 들어온다.
보관과 스케줄링(월 1회 배치 스냅샷)은 호스트의 몫이다.

## 사분면

노력 반복성 × 효과 반복성. `set_and_forget`이 다른 사분면을 압도한다 — 한 번
세팅하면 매년 자동으로 돌아오므로, 절감액이 다소 작아도 위로 띄울 가치가 있다.

|              | 1회 효과      | 반복 효과            |
|--------------|---------------|----------------------|
| **1회 노력** | `one_off`     | **`set_and_forget`** |
| **반복 노력**| `poor`        | `maintenance`        |

## 프로필 자동 수집

`Profile` 필드는 30개가 넘는다. 사용자가 손으로 채울 규모가 아니므로 외부
원천에서 끌어온다. `sources.py` 가 그 수집 규약이다.

**모름과 0을 구분한다.** 이게 이 계층의 존재 이유다. 자동 수집에서 값이 비어
있는 것은 "쓰지 않았다"가 아니라 대개 "아직 못 가져왔다"는 뜻인데, 둘을 합치면
에이전트가 "공제 대상이 아닙니다"라고 단정하게 된다. 그래서 카탈로그는 자격 미달
(`ineligible`)과 자료 부족(`indeterminate`)을 따로 돌려주고, 후자에는 무엇을
어디서 채워야 하는지가 함께 담긴다.

세 단계로 의미가 갈린다 — **키 없음 = 모름**, **`null` = 없는 것으로 확인됨**,
**`0` = 실제로 0원**. 사용자가 "중소기업에 다닌 적 없다"고 답한 것을 모름으로
두면 같은 질문을 계속 하게 된다.

**필드마다 출처와 기준일을 남긴다.** 숫자의 신뢰도는 출처에 달렸고, 에이전트가
"간소화자료 기준입니다"와 "3월에 알려주신 값입니다"를 구분해 말할 수 있어야 한다.
스냅샷 비교에서도 값이 변한 것과 더 나은 출처를 확보한 것은 다른 사건이다.

| 원천 | 권위 | 주로 담당하는 값 |
|------|-----|-----------------|
| 연말정산 간소화 자료 | 40 | 의료비, 기부금, 카드 사용액, 월세, 연금·청약 납입 |
| 원천징수영수증 | 40 | 총급여, 소득공제·세액공제 총액 |
| 금융 마이데이터 | 30 | 금융소득, ISA 납입액 |
| 사용자 | 20 | 무주택 세대주 여부, 나이, 부양 자녀 수 등 |
| 추정 | 10 | 다른 값에서 유도 |

간소화자료를 사용자 입력보다 위에 두는 이유는 국세청이 실제 신고에서 쓰는 자료가
그것이기 때문이다. 다만 **같은 권위의 두 원천이 다른 값을 주면 조용히 하나를 고르지
않는다.** 간소화자료와 마이데이터의 카드 사용액이 어긋나는 것은 사용자가 알아야 할
사실이지 도구가 대신 판단할 문제가 아니다. 최신 값을 잠정 채택하되 충돌은 그대로
보고한다.

실제 커넥터(홈택스, 마이데이터)는 인증과 기관 허가가 필요해 도구 계층 밖이다.
매핑(`HOMETAX_CATEGORY_MAP`)은 커넥터가 붙기 전에도 확정해 둘 수 있어 먼저 만들었다.

## 변화 감지: 실제 변화와 데이터 정정을 가른다

자동 수집을 쓰면 값이 달라지는 이유가 둘로 갈린다. 사용자의 상황이 실제로 바뀌었거나
(이직, 출산), 더 정확한 자료를 확보했거나(어림값 → 간소화자료). 이 둘을 합치면
"소득이 늘었네요"라고 알림이 나가는데 사실은 제대로 된 자료를 처음 본 것뿐일 수 있다.
알림 한 번 잘못 나가면 사용자는 알림을 끄고, 그러면 정작 중요한 순간에 닿지 못한다.

`diff_profile_data` 는 변화를 다섯으로 나눈다.

| 종류 | 뜻 | 알림 | 재계산 |
|------|-----|-----|-------|
| `value_changed` | 같은 권위의 출처가 다른 값 — 생활 사건 | O | O |
| `corrected` | 더 나은 출처가 다른 값 — 데이터 정정 | X | O |
| `enriched` | 몰랐던 값을 새로 확보 | X | O |
| `source_upgraded` | 값은 같고 출처만 개선 | X | X |
| `lost` | 있던 값이 사라짐 | X | O |

`life_events()` 로 알릴 것만 걸러내고 `needs_recompute()` 로 다시 계산할지 정한다.
출처를 모르는 `Profile` 두 개를 비교하는 `diff_snapshots` 도 남아 있지만, 자동 수집을
쓴다면 출처 없이는 실제 변화와 정정을 구분할 수 없다.

## 액션 카탈로그

액션마다 도구를 하나씩 늘리면 에이전트가 매번 "뭘 불러야 하지"를 고르게 된다.
평가 함수를 레지스트리(`catalog.py`)에 모아두고 진입점 하나만 노출한다 —
`recommend_actions(profile, year, view)`.

| 액션 | 공제 유형 | 사분면 |
|------|-----------|--------|
| 연금저축·IRP 납입 | 세액공제 | `set_and_forget` |
| 주택청약종합저축 납입 | 소득공제 | `set_and_forget` |
| 중소기업 취업자 감면 | 세액감면 | `set_and_forget` |
| ISA 납입 | 분리과세 | `set_and_forget` |
| 월세 세액공제 | 세액공제 | `maintenance` |
| 의료비 세액공제 | 세액공제 | `maintenance` |
| 기부금 세액공제 | 세액공제 | `maintenance` |
| 결제수단 전환 | 소득공제 | `set_and_forget` |

**소득공제와 세액공제를 섞지 않는다.** 소득공제는 과세표준을 줄이므로 절감액이
한계세율에 비례하고, 세액공제는 세액을 직접 줄이므로 소득과 무관하다. 총급여
3,800만원 기준으로 같은 120만원이 소득공제면 19.8만원, 세액공제면 132만원을
줄인다. 한 통에 넣으면 랭킹이 통째로 틀어진다.

**자격 미달도 사유와 함께 돌려준다.** 조용히 빼면 사용자가 "왜 나는 이게
안 뜨죠?"라고 물었을 때 에이전트가 답하지 못한다.

## 의료비 세액공제

소득세법 제59조의4 제2항. 총급여의 3%를 넘는 부분만 대상이고, 공제율은 일반 15%,
난임시술비 30%, 미숙아·선천성이상아 20%다.

**700만원 한도는 '그 밖의 의료비'에만 붙는다.** 본인·6세 이하·65세 이상·장애인·
중증질환자 의료비와 미숙아·난임 의료비는 한도가 없다. 모든 의료비에 한도를 씌우면
부양가족 의료비가 큰 납세자의 공제액이 크게 과소 계산된다 — 65세 부모 의료비
2,000만원 표본에서 195만원 차이가 났다.

**3% 기준선은 '그 밖의 의료비'에서 먼저 차감되고, 모자라면 한도 없는 호에서 마저
뺀다.** 제3호 미숙아·선천성이상아 의료비는 제1·2호 의료비 합계와 기준금액을
비교하고, 제4호 난임시술비는 제1~3호 합계와 비교한다. 법정 순서에 따라 남은
미달분만 차감하며, 이를 임의의 유리한 해석으로 표시하지 않는다.
[소득세법 제59조의4](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=04&joNo=0059&lsiSeq=280405&urlMode=lsScJoRltInfoR)

## 신용카드 등 소득공제

조세특례제한법 제126조의2. 총급여의 25%를 넘는 사용분부터 공제가 시작되고,
결제수단별로 공제율이 다르다 — 신용카드 15%, 직불·선불·현금영수증 30%,
문화체육 30%(총급여 7천만 이하), 전통시장·대중교통 40%.

**최저사용금액은 공제율이 낮은 결제수단부터 차감된다.** 이 순서가 결과를 좌우한다.
안분해서 빼는 순진한 구현은 공제액을 과소 계산한다 — 총급여 5,000만·신용카드
2,000만·체크 500만 표본에서 53만원 차이가 났다.

그래서 실제 행동 지렛대는 "신용카드는 최저사용금액까지만, 나머지는 체크카드로"가
된다. 15% 구간이 차감에 다 소진되고 30%가 온전히 남기 때문이다. 카탈로그의
`payment_method_switch` 가 이 전환의 효과를 계산한다. 지갑에서 들고 다니는 카드를
바꾸는 1회 결정이라 `set_and_forget` 사분면에 들어간다.

2025년 기본한도는 총급여 7천만 이하 300만원, 초과 250만원이다. 자녀 수에 따른
한도 확대는 2026년부터 적용되므로 2025년 계산에는 넣지 않는다.
추가한도는 전통시장·대중교통 합계 200만원이며, 총급여 7천만 이하는 문화체육을
포함해 300만원이다.

## 금융소득 종합과세

이자·배당 합계가 2,000만원을 넘으면 소득세법 제62조에 따라 두 가지로 계산해
**큰 쪽**을 택한다. 종합과세가 오히려 원천징수보다 가벼워지는 역전을 막기 위한
장치라, 둘 중 하나만 계산하면 세액이 과소 산출된다.

```
① 일반산출세액 = 2,000만 × 14% + (초과 금융소득 + 다른 종합소득 − 소득공제) × 기본세율
② 비교산출세액 = 금융소득 전체 × 14% + (다른 종합소득 − 소득공제) × 기본세율
산출세액 = MAX(①, ②)
```

여기 쓰는 14%는 **소득세만**이다. 지방소득세 포함 15.4%를 넣으면 마지막에 10%를
다시 더하면서 이중 계산이 된다. 룰셋에 두 값을 분리해 둔 이유다.

**`estimate_tax` 는 산출세액이 아니라 총 세부담을 돌려준다.** 금융소득이 기준금액
이하면 그 세금은 원천징수로 끝나 산출세액에 잡히지 않다가, 초과하면 산출세액 안으로
들어온다. 산출세액만 보고하면 같은 이름의 숫자가 경계 양쪽에서 다른 것을 가리켜
비교가 불가능해진다 — 하필 그 경계가 이 도구가 감시하는 지점이다. 총 세부담으로
통일하면 경계에서 연속이다(`test_no_cliff_in_total_burden_at_the_threshold`).

세액공제는 종합소득 산출세액에서만 차감되므로 분리과세분은 `separate_financial_tax`
로 따로 담는다.

## 값 환산 방식

순위 기준은 **자기 지평 위의 현재가치(PV)**, 표시용은 **공통 지평 위로 편
연간 환산액**이다. 각자 다른 지평에서 구한 연간 환산액끼리는 비교가 성립하지
않는다 — 1회성 500만원의 1년 환산액은 500만원, 매년 100만원의 10년 환산액은
100만원이라, 그대로 비교하면 반복 효과가 부당하게 저평가된다.

## 불확실성: 상한이 아니라 지속확률

효과가 얼마나 오래 갈지는 모른다. 그 모름을 하드 컷("10년째까지 100% 확실하고
11년째부터 0%")으로 표현하면 현실의 어떤 것도 그렇게 작동하지 않는다는 문제가
생긴다. 게다가 상한은 전역이라 항목별로 다른 확신도를 담지 못한다 —
연금저축(본인이 계약한 법적 구조)과 월세(자가 구매로 언제든 끊김)를 같은
확신도로 취급하면 순위가 왜곡된다.

대신 `assumptions.py` 에서 항목별 **지속확률**을 준다. 수학적으로는 할인율에
그대로 흡수된다:

```
(1 + 실효할인율) = (1 + 할인율) / 지속확률
```

| 액션 | 지속확률 | 근거 |
|------|---------|------|
| 중소기업 감면 | 1.00 | 법정 감면 기간. 불확실성 없음 |
| 연금저축·IRP | 0.97 | 중도해지 불이익으로 유지 유인이 큼 |
| ISA | 0.95 | 의무보유는 확정이나 금융소득 발생에 의존 |
| 주택청약 / 기부금 | 0.90 | 무주택 요건·본인 의지에 의존 |
| 월세 | 0.85 | 자가 구매·전세 전환으로 끊김 |
| 의료비 | 0.80 | 지출 반복을 전제할 수 없음 |

상한(기본 30년)은 폭주 방지용 바깥 울타리로만 남는다. 지속확률 0.85면 15년
이후 15년치를 통째로 더해도 기여가 5% 미만이라 실제로 구속력을 갖는 일은 드물다.

**이 값들은 세법이 아니라 판단이다.** 그래서 `rules/data/*.json`(확인하면 맞고
틀림이 정해지는 사실)과 `assumptions.py`(추정)를 분리한다. 한 파일에 섞으면
어느 쪽이 검증된 것인지 알 수 없게 된다. 지속확률 가정은 결과의
`rationale.assumptions` 에 자동으로 명시된다.

## 범위

세액 계산은 규칙 기반이라 결정론적이고 검증 가능하다. 이 도구의 경계를 거기에
둔다. 상품 추천이나 투자 판단은 같은 방식으로 검증할 수 없으므로 다루지 않는다.

## 세법 데이터 검증

`rules/data/2025.json`은 **재검증 중**(`verified: false`)이다. 의료비 두 항목의
공제율이 서로 바뀐 오류를 발견해 수정했고, 전체 검증 완료 표시는 철회했다.
이전 검토 기록은 `verification.checked`, 재대조한 범위와 근거는
`verification.rechecked`에 구분해서 기록한다. 테스트 통과만으로 세법 데이터가
맞다고 판단하지 않으며, 법령·국세청 원천과 독립적으로 대조해야 한다.

세율표는 소득세법 제55조의 누적액 형태(예: "5,000만 초과 시 624만원 + 초과분
24%")를 누진공제 형태로 환산해 8개 구간 전부 일치를 확인했고, 그 값들을
`test_brackets_match_statute` 로 고정해 두었다 — 부주의한 수정은 테스트에서 걸린다.

2차 자료가 엇갈린 항목은 법령 원문을 기준으로 삼았다. 중소기업 취업자 감면
한도가 그런 경우로, 일부 자료의 150만원은 개정 전 수치이며 조세특례제한법
제30조 현행 조문은 청년·비청년 모두 200만원이다.

**아직 검증하지 않은 연도**의 데이터로 계산하면 결과의 `rationale.warnings` 에
경고가 자동으로 붙는다. 이 메커니즘은 계속 살아 있다.

### 알려진 공백

데이터 오류가 아니라 구현 범위의 한계다. `verification.known_gaps` 에도 기록되어 있다.

- 신용카드 소비증가분 추가공제. 연도마다 도입 여부와 요건이 달라지는 한시 조치다
- 배당가산액(Gross-up)과 배당세액공제. 둘은 이중과세 조정을 위해 서로 상쇄되므로
  한쪽만 넣으면 오히려 부정확해진다 — 내국법인 배당을 구분해 받을 수 있게 되면 함께 구현

- 기부금 소득금액 대비 공제 한도
- 신용카드 등 사용금액 소득공제


### ISA 투자 시나리오의 범위

`simulate_isa`는 올해 소득세·연말정산 환급액과 독립적으로 **추가 납입분의
보유기간 전체 투자 세금**을 비교한다. 연 수익률을 단리로 적용하며, 기본
보유기간은 3년이다. 계좌 전체 순이익에 비과세 한도를 한 번 적용하고,
절세액은 종료 시점의 1회성 혜택으로 평가한다.

입력 `holding_years`로 보유기간을, `existing_net_gain`으로 추가 납입분을 제외한
계좌의 종료 시점 예상 순손익을 지정한다. 후자의 기본값 0은 명시적인 가정이다.
기존 수익으로 비과세 한도를 이미 소진한 경우 그 한도를 다시 주지 않는다.
일반계좌 수익 전액이 15.4% 원천징수되는 경우만 비교하며, 가입 자격 판정,
비과세 매매차익, 종합과세, 수수료, 이월 납입한도는 지원하지 않는다.
자동 추천의 역산 수익률은 가상 시나리오이므로 실제 예상 수익률과 기존 손익으로
다시 계산해야 한다.

ISA 응답은 `tax_scope: investment_holding_period`, `total_saving`,
`normal_account_tax`, `isa_account_tax`, `projected_gain`, `holding_years`를 제공한다.
두 세금 필드는 추가 납입에 따른 증분 세금이다. 기존의 `annual_saving`,
`baseline_total`, `simulated_total`은 ISA 응답에서 제거했으므로 연동 코드를 갱신해야 한다.
연금 시뮬레이터 응답은 그대로 유지한다.

근거: [KB국민은행 ISA 세제 혜택](https://obank.kbstar.com/quics?page=C041167),
[미래에셋증권 ISA 가입자격 및 종류](https://trading.securities.miraeasset.com/hks/hks4659/n02.do).
이는 해당 투자 시나리오의 근거이며 전체 세법 규칙 검증 완료를 뜻하지 않는다.


### 주거·문화비 입력 보완

`is_homeless_household_head_spouse`로 배우자 자격을 입력하며, 세대주가 아닌데
배우자 여부를 모르면 추천은 자격 미달 대신 추가 질문을 반환한다.
[국세청 주택마련저축 안내](https://www.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=239022&mi=40610)

중복 없이 분리해서 입력한다. 총급여 7천만원 초과자는 문화비를 버리지 않고
실제 결제수단의 일반 공제율로 계산한다. 이때 `culture_credit_card_spending`과
